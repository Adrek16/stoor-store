## 2. تدفّق الطلب الجديد (أهم تغيير وظيفي)

### 2.1 التدفّق المعتمد

```
1) عميل مسجّل يتصفّح ويضيف للسلة
   └─ السلة محفوظة في الخادم لكل عميل — لا مخزون، لا حجز، لا خصم.
   └─ الزائر يُطلب منه تسجيل الدخول قبل الإضافة.

2) العميل المسجّل يرسل الطلب من /checkout
   └─ يُنشأ طلب بحالة «جديد» (new)، مربوطاً بحسابه (`customer_id`)، وبدون خصم مخزون.

3) صفحة التأكيد /order/[id]
   └─ «وصل طلبك — سنتواصل معك على واتساب أو هاتف لتأكيده»
   └─ زر واتساب يحمل رقم الطلب والمنتجات تلقائياً.

4) المدير يفتح الطلب في اللوحة
   └─ يرى بيانات العميل والمنتجات.
   └─ يتواصل معه على واتساب أو هاتف (أزرار جاهزة في اللوحة).
   └─ عند الاتفاق يضغط «تأكيد الطلب وخصم المخزون».

5) الخصم ذرّي في قاعدة البيانات
   └─ يتحقق من توفر كل قطعة/لون أولاً.
   └─ إن توفّرت: يخصم المخزون ويحوّل الحالة إلى «مؤكد».
   └─ إن نفدت: يرفض ويُعلم المدير بالقطع الناقصة، ويبقى الطلب «جديد».

6) الإلغاء
   └─ قبل التأكيد: لا حركة مخزون.
   └─ بعد التأكيد: يُعاد المخزون عبر release_order_stock.
```

### 2.2 الحالة الحالية في الكود (يجب تغييرها)

- `src/app/api/orders/route.ts` يستدعي `reserve_stock` **فور إنشاء الطلب** (السطر ~184). هذا يخالف القرار: يجب أن يبقى الطلب بلا خصم حتى يؤكّده المدير.
- لوحة المدير فيها بالفعل `release_order_stock` لإرجاع المخزون عند الإلغاء — تُعاد استخدامها. أما `reserve_order_stock` فلا تُستخدم عند إنشاء الطلب ولا عند إعادة فتحه؛ الخصم يصير عبر `confirm_order_stock` فقط.

### 2.3 التغييرات المطلوبة

| # | التغيير | الملف |
|---|---|---|
| 1 | إزالة `reserve_stock` من إنشاء الطلب، وإزالة رفض 409 عند النفاد | `src/app/api/orders/route.ts` |
| 2 | عمود `orders.stock_state`: `none` / `reserved` / `released` | `supabase/schema.sql` |
| 3 | دالة `confirm_order_stock(order_id)` ذرّية: فحص ثم خصم ثم تحويل الحالة | `supabase/schema.sql` |
| 4 | زر «تأكيد الطلب وخصم المخزون» + معالجة النقص | لوحة المدير (انظر خطتها) |
| 5 | نص صفحة التأكيد: «بانتظار تأكيد المدير عبر واتساب/هاتف» | `src/app/order/[id]/OrderView.tsx` |
| 6 | زر واتساب في صفحة التأكيد برسالة جاهزة | نفس الملف |
| 7 | منع العميل من رؤية «تم الشحن» أو أي حالة غير موجودة | `src/lib/orders.ts` |
| 8 | ربط كل طلب بحساب عميل: `orders.customer_id` + فهرس | `supabase/schema.sql` |
| 9 | رفض إنشاء طلب بلا جلسة عميل (401) | `src/app/api/orders/route.ts` |

### 2.4 مخاطر يجب معالجتها

- **البيع المزدوج:** بين إرسال الطلب وتأكيد المدير قد يشتري شخص آخر. الحل: التأكيد ذرّي، وإن نقصت الكمية يُبلَّغ المدير ويعتذر للعميل.
- **طلبات متروكة:** تبقى «جديدة» بلا خصم — لا تضرّ المخزون. يمكن لاحقاً إلغاء تلقائي بعد ٧ أيام.

### 5.4 السلة — مرتبطة بالعميل المسجّل

**القاعدة الحاكمة:** لا سلة للزائر. زر «أضف إلى السلة» متاح فقط بعد تسجيل الدخول، ولكل عميل **سلة واحدة محفوظة على الخادم** تتبعه على كل أجهزته.

#### أ) السلوك

| الحالة | السلوك |
|---|---|
| زائر يفتح السلة | يرى دعوة لتسجيل الدخول بدل محتوى السلة. |
| زائر يضغط «أضف إلى السلة» | يُحوَّل إلى `/account?next=…` مع رسالة «سجّل دخولك لإضافة المنتجات إلى سلتك». |
| عميل مسجّل | تُضاف القطعة إلى سلته في الخادم فوراً، ويظهر العدد في الهيدر. |
| تسجيل الخروج | تُفرَّغ السلة من الذاكرة فقط، وتبقى محفوظة في الخادم. |
| تسجيل الدخول من جهاز آخر | تظهر نفس السلة تلقائياً. |
| سلة محلية قديمة (نسخة سابقة) | تُدمج **مرة واحدة** في سلة الخادم بعد أول تسجيل دخول، ثم تُمسح. |

> زر «اطلب عبر واتساب» في صفحة المنتج يبقى متاحاً للزائر لأنه تواصل مباشر، لكنه **لا ينشئ سلة ولا طلباً** في الموقع.

#### ب) قاعدة البيانات

```sql
create table public.customer_carts (
  customer_id uuid not null references auth.users(id) on delete cascade,
  product_id  text not null references public.products(id) on delete cascade,
  option      text not null default '',
  color       text not null default '',
  qty         smallint not null check (qty between 1 and 20),
  updated_at  timestamptz not null default now(),
  primary key (customer_id, product_id, option, color)
);
```

- RLS مفعّل بلا سياسات عامة؛ الوصول من الخادم بـ `service_role` فقط.
- السلة **لا تحجز مخزوناً ولا تخصم منه** — مجرد نوايا شراء.
- حذف منتج يحذف سطره من كل السلات (`on delete cascade`).

#### ج) المسارات

| المسار | الوظيفة |
|---|---|
| `GET /api/account/cart` | سلة العميل الحالي (محمي بالجلسة) |
| `POST /api/account/cart` | إضافة/زيادة قطعة |
| `PATCH /api/account/cart` | تعديل الكمية |
| `DELETE /api/account/cart` | حذف قطعة أو تفريغ السلة |

- كل مسار يتحقق من الجلسة ويرفض 401 لغير المسجّل.
- الأسعار تُقرأ من الكتالوج على الخادم، ولا تُقبل من العميل.
- حد أقصى ٢٠ قطعة من نفس المنتج/اللون، و٥٠ سطراً للسلة.

#### د) الواجهة

- **بدون** شريط شحن مجاني، **بدون** حقل كوبون.
- سطر ثابت: «الاستلام من المتجر — الدفع عند الاستلام أو تحويل/محفظة».
- «أكمل إطلالتك»: ٤ منتجات مقترحة.
- ملخّص: المجموع الفرعي = الإجمالي. **حذف** سطر «شامل ضريبة القيمة المضافة».
- زر «إتمام الطلب» + ملاحظة أن التأكيد يتم عبر واتساب/هاتف.
- درج السلة والهيدر يقرآن العدد من سلة الخادم، لا من `localStorage`.

**الملفات:** `src/components/cart/CartProvider.tsx` (إعادة كتابة) · `src/app/cart/page.tsx` · `src/components/cart/CartDrawer.tsx` · `src/app/api/account/cart/route.ts` (جديد) · `src/lib/cart/store.ts` (جديد) · `supabase/schema.sql`.

### 5.5 إتمام الطلب

> **يتطلب جلسة عميل.** لا إتمام للزائر — لأن السلة والطلب مرتبطان بحساب العميل.

| الحقل | التفصيل |
|---|---|
| الاسم | مطلوب — يُملأ تلقائياً من الملف الشخصي ويبقى قابلاً للتعديل |
| الجوال | مطلوب — يُملأ تلقائياً إن وُجد، صيغة يمنية (`7xxxxxxxx` أو `+967…`) |
| العنوان | **غير موجود** (استلام من المتجر) |
| الملاحظات | اختياري |
| طريقة الدفع | عند الاستلام · تحويل بنكي · محافظ محلية (من إعدادات المدير) |
| رسوم | **لا توجد** — لا شحن ولا ضريبة |

- الطلب يُحفظ مع `customer_id` من الجلسة — لا طلبات مجهولة.
- إضافة `profiles.phone text` لتعبئة الجوال تلقائياً (اختياري).
- بعد الإرسال: رسالة واضحة «طلبك ليس مؤكداً بعد — سنتواصل معك لتأكيده».
- عرض بيانات الحساب/المحفظة المختارة + رفع الإيصال (للتحويل والمحافظ).
- لا تُعرض أي بيانات بطاقة.

**الملفات:** `src/app/checkout/page.tsx` · `src/app/api/checkout/config/route.ts` · `src/app/api/orders/route.ts` · `src/lib/orders.ts`.

### 5.6 تأكيد الطلب

- رقم الطلب + التاريخ + الفاتورة.
- **خط زمني:** جديد → مؤكد → مكتمل (أو ملغى).
- نص: «بانتظار تواصل المدير على واتساب/هاتف».
- زر واتساب برسالة جاهزة: «طلب رقم ST-… أرغب بتأكيده».
- رفع إيصال التحويل/المحفظة + حالة المراجعة.
- «إعادة الطلب» تعيد المنتجات للسلة.

**الملفات:** `src/app/order/[id]/OrderView.tsx`.

### 5.7 حساب العميل

- تسجيل/دخول بالبريد (موجود).
- **«سلتي»:** تظهر محفوظة بعد الدخول من أي جهاز، وتُمسح بعد إتمام الطلب.
- «طلباتي» بحالات ملوّنة + إعادة الطلب.
- بيانات الملف الشخصي (الاسم، الجوال) تُستخدم لتعبئة الإتمام تلقائياً.
- مفضلة (اختياري لاحقاً).

## 6. نظام التقييمات والنجوم — خطة كاملة

### 6.1 القواعد

1. **من يقيّم؟** عميل مسجّل، وله طلب **مؤكد أو مكتمل** يحتوي المنتج.
2. **كم مرة؟** تقييم واحد لكل عميل لكل منتج. يمكن تعديله خلال ١٤ يوماً.
3. **المراجعة:** كل تقييم يبدأ `pending`، ولا يظهر إلا بعد موافقة المدير.
4. **المحتوى:** نجوم 1–5 إلزامية، تعليق اختياري (حتى ١٠٠٠ حرف)، اسم يظهر كـ«أحمد م.».
5. **ممنوع:** تقييمات وهمية أو من غير مشترين.

### 6.2 قاعدة البيانات

```sql
create table public.product_reviews (
  id uuid primary key default gen_random_uuid(),
  product_id text not null references public.products(id) on delete cascade,
  customer_id uuid not null references auth.users(id) on delete cascade,
  order_id text references public.orders(id) on delete set null,
  rating smallint not null check (rating between 1 and 5),
  body text check (char_length(body) <= 1000),
  status text not null default 'pending'
    check (status in ('pending','approved','rejected')),
  admin_reply text check (char_length(admin_reply) <= 1000),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (product_id, customer_id)
);
```

- فهرس على `(product_id, status)`.
- RLS: لا قراءة عامة؛ القراءة من الخادم فقط.
- متوسط التقييم يُحسب من المعتمدة، ويُحدَّث في `products.rating` و`products.reviews` (كاش) عبر trigger أو عند الاعتماد.

### 6.3 الواجهة

| الموضع | العرض |
|---|---|
| البطاقة | نجوم صغيرة + العدد (إن وُجد) |
| صفحة المنتج | متوسط + عدد + توزيع النجوم + قائمة التعليقات |
| نموذج التقييم | يظهر فقط لمن اشترى — نجوم + تعليق + إرسال |
| الرئيسية | ٦ آراء معتمدة (مختارة) في `Testimonials` |
| JSON-LD | `aggregateRating` من القيم الحقيقية فقط |

### 6.4 المسارات

| المسار | الوظيفة |
|---|---|
| `GET /api/products/[id]/reviews` | التعليقات المعتمدة + ملخّص التقييم + أهلية العميل للتقييم |
| `POST /api/products/[id]/reviews` | إرسال تقييم (محمي بجلسة العميل + التحقق من الشراء + حد ٥/ساعة) |
| `GET /api/reviews` | أحدث التقييمات المعتمدة عبر المنتجات — لقسم «آراء العملاء» في الرئيسية |

### 6.5 مكافحة التلاعب

- تحقق من الشراء على الخادم (لا نثق بالعميل).
- تقييم واحد لكل منتج/عميل (قيد فريد).
- حد معدّل: ٥ تقييمات/ساعة.
- مراجعة يدوية قبل النشر.

## 7. الترتيب المبني على بيانات العملاء

### 7.1 المبدأ

الترتيب لا يعتمد على ما يدخله المدير، بل على ما يفعله العملاء فعلاً:

| الترتيب | المصدر | ليس |
|---|---|---|
| **الأكثر مبيعاً** | عدد القطع المباعة من الطلبات **المؤكدة والمكتملة** | شارة يدوية أو رقم يكتبه المدير |
| **الأعلى تقييماً** | متوسط **تقييمات العملاء المعتمدة** | حقل `rating` ثابت في المنتج |
| **الأكثر رواجاً** | مزيج محسوب: مبيعات + تقييم + حداثة | `sort_order` اليدوي وحده |

### 7.2 كيف تُحسب

**أ) الأعلى تقييماً — متوسط مرجّح (Bayesian):**

```
score = (v / (v + m)) × R  +  (m / (v + m)) × C

v = عدد التقييمات المعتمدة
R = متوسط تقييمات المنتج
m = 5  (وزن أدنى)
C = متوسط تقييمات المتجر كله
```

- يمنع منتجاً بتقييم ٥ نجوم من تقييم واحد أن يتصدّر.
- لا يدخل المنتج قائمة «الأعلى تقييماً» قبل **٣ تقييمات معتمدة**.

**ب) الأكثر مبيعاً — وحدات مباعة:**

- تُحسب من `orders.items` للطلبات بحالة `confirmed` أو `completed`.
- تُستثنى `cancelled` و`new` (غير المؤكدة).
- تُزاد عند **تأكيد المدير** (نفس لحظة خصم المخزون) — اتساق كامل مع تدفّق الطلب.
- الإلغاء بعد التأكيد يُنقص العدد مرة واحدة.

**ج) الأكثر رواجاً — درجة مركّبة:**

```
popularity = 0.6 × مبيعات مُطبَّعة
           + 0.3 × تقييم مُطبَّع
           + 0.1 × حداثة (الأحدث أعلى)
```

### 7.3 قواعد العرض

1. **لا شارة «الأكثر مبيعاً»** لمنتج بلا مبيعات حقيقية.
2. إذا كان القسم جديداً وبلا مبيعات كافية (أقل من ٥ طلبات مؤكدة): يُعرض الترتيب الافتراضي بوسم **«مختارة بعناية»** بدل «الأكثر مبيعاً» — لا نُختلق أرقاماً.
3. «الأعلى تقييماً» يحتاج ٣ تقييمات معتمدة على الأقل.
4. المدير **لا يعدّل** `rating` أو `reviews` يدوياً. يستطيع فقط:
   - ترتيباً تحريرياً (`sort_order`، يُضبط تلقائياً عند الإضافة) يُستخدم **كفاصل تعادل فقط** — ولا يرفع منتجاً إلى قائمة «الأكثر مبيعاً».
   - شارات مناسبات: «جديد»، «إصدار محدود»، «خصم».
   - **لا** شارة «الأكثر مبيعاً» يدوياً — تُشتق تلقائياً.
5. التقييم من مشترٍ فقط، واحد لكل منتج — يمنع التلاعب.

### 7.4 التنفيذ والأداء

- أعمدة محسوبة مسبقاً في `products`:
  - `rating numeric` — **يُعاد استخدامه**: المتوسط المرجّح (بدل قيمة يدوية).
  - `reviews int` — **يُعاد استخدامه**: عدد التقييمات المعتمدة.
  - `sales_count int` — **عمود جديد**: وحدات مباعة.
  - `popularity_score numeric` — **عمود جديد**: الدرجة المركّبة.
- تُحدَّث عبر triggers:
  - اعتماد/رفض/حذف تقييم → تحديث `rating` و`reviews`.
  - تأكيد/إلغاء طلب → تحديث `sales_count`.
- لا تجميع على `orders.items` وقت كل طلب صفحة — القراءة من الأعمدة الجاهزة.
- بعد كل تحديث: `revalidateTag("catalog")`.
